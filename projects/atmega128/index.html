ATmega128 from the Registers Up

ATmega128 at register level: timer math checked on the scope, a keypad bug traced over four seminars, Aug. –⁠ Dec. 2019

From August to December 2019, as an undergraduate researcher at IHLAB (Tech University of Korea), I learned the ATmega128 microcontroller from the registers up, one peripheral at a time, and presented each step at the lab seminar. On the lab’s training kit I programmed GPIO, external interrupts, Timer2 in all four of its modes, a character LCD with custom characters, and USART serial, working the numbers out first and then checking them on the oscilloscope or a PC terminal. The series ended with the choice of a DYNAMIXEL robot arm as the winter project, the start of my legged-robot work.

What this project shows

Derive first, then measure

For the 1-second exercise in three Timer2 modes, I worked the constants out on paper from the kit’s 14.7456 MHz crystal: tick length, overflow count, compare value, duty cycle. Then I checked each period with the oscilloscope’s cursors in normal, CTC and fast PWM modes.

Stay with a bug until it is understood

The keypad took four seminars: first it read only 0, then one press filled all four digits. I filmed it at each of those seminars, fixed one cause at a time, and said plainly what still did not work.

Down to the bit

I drew my name as six custom LCD characters and worked out their 48 bytes by hand. When the screen stayed blank, the cause was in the program: it never wrote a character code to display memory, so nothing told the display to show them.

Questions answered in writing

Six talks open with FEEDBACK slides that follow up the previous talk’s questions, 37 slides in all. I also corrected a textbook figure, and my own description of a register bit a week after presenting it.

Derive on paper, then check on the scope

  • One clock behind every constant. The kit runs on a 14.7456 MHz crystal. With the /8 prescaler, one timer tick is 0.5425 µs and one 256-count overflow 138.89 µs, so 7200 overflows make a second. I worked out each mode’s constants this way and used them in its code.
  • Three modes, one target. For a 1-second period, normal mode toggles a pin every 3600 overflows. CTC mode uses /1024 (69.44 µs per tick), OCR2 = 72 and 100 compare matches. In fast PWM mode, the 7200 periods of each second are counted in software and split at 6000, an 83% duty cycle. In all three, the scope cursors read Δ1.00 s.
  • A correction for the record. The CTC constant is off by one. In CTC mode the counter runs from 0 to OCR2, so OCR2 = 72 means 73 ticks per match, and the code as written gives a period of 1.014 s, not 1.000 s. The hand-placed cursors did not catch the 14 ms difference; OCR2 = 71 gives exactly 1.000 s.
  • A datasheet question, tested. To follow up a seminar question about when a new OCR2 value takes effect in phase-correct PWM, I wrote two versions, one rewriting OCR2 in the overflow interrupt and one in both the overflow and compare interrupts, and marked up the datasheet’s timing diagram for each. The scope’s frequency readout showed 3.61407 kHz for both, against the 3614.12 Hz expected from 14.7456 MHz ÷ (8 × 510).

One keypad bug, four seminars

  • One cause at a time. In October the 4×4 keypad showed only 0. By 7 Nov keys registered, but one press filled all four digits. For 14 Nov I fixed two errors in the scan, rows driven high where they should have been driven low and a key-index formula that gave the wrong numbers, but the flood remained: the loop read a held key again on every pass.
  • From a delay to edge detection. A 0.25 s hold-off after each digit then gave one digit per press, as long as the key was released within 0.25 s (14 Nov). In the same talk I said that versions driven by interrupts or the timer did not work yet. A week later I replaced the delay with edge detection: a key counts only when the scan result changes.
  • What a button really does. In October, INT0 on a falling edge toggled all eight LEDs. In a December drill, where each INT0 press stepped through four LED patterns, I boxed two spikes on the scope just before a clean edge: switch bounce, each spike an extra edge that the interrupt could count as a press.

My name in 48 bytes

  • Pixel by pixel. The LCD controller has a small RAM, CGRAM, for characters the user draws. I drew the three syllables of my name (양건모) on 5 × 8 grids, two characters per syllable, worked out the 48 bytes by hand, and wrote them to CGRAM with the set-address commands 0x40 to 0x68.
  • A blank screen, explained. On 14 Nov the LCD stayed blank. The code wrote the glyphs into CGRAM but never wrote a character code into DDRAM, the memory that holds what the screen shows, and it set the cursor before initializing the LCD. On 21 Nov, with initialization first and six DDRAM writes (codes 0x00–0x05), my name appeared.

Reading the board and the books

  • The kit’s schematic, block by block. On 19 Sep I went through the schematic of the lab’s ATmega128 training kit one block at a time: oscillator, reset, analog supply filter, switches, LEDs, and the RS-232 and USB interfaces. The schematic is the kit’s own sheet (“ATMEGA128KIT”, dated 2010), not my design. My part was a note on what each component does, such as the diode that drains the leftover voltage at power-off.
  • One crystal, followed into the firmware. My note on the oscillator says the kit uses a 14.7456 MHz crystal to match the serial clock. On 21 Nov I boxed its column in the baud-rate table (0.0% error), set UBRR to 14745600 ÷ (16 × 115200) − 1 = 7, and a PC terminal received “Serial Comm Test”.
  • Sources checked, my own included. A textbook figure labelled +10 V on an RS-232 line as mark “0”. I corrected it to space, with mark “1” at the negative level, as in the level table on the same slide. My 21 Nov script said the UCPOL bit is used only in transmit mode; after a question, the 28 Nov talk corrected it: UCPOL is for synchronous mode, where it sets when output data changes and when input data is sampled.

한국어 요약

2019년 8월부터 12월까지 한국공학대학교 IHLAB 학부연구생으로 ATmega128을 레지스터 수준에서 주변장치 하나씩 익히고, 단계마다 랩 세미나에서 발표했습니다. 타이머 상수는 14.7456 MHz 클럭에서 손으로 계산한 뒤 오실로스코프로 확인했고(일반·CTC·고속 PWM 모드 모두 커서 간격 1.00초), 위상 정정 PWM 출력은 3.61407 kHz로, 클럭에서 예상되는 3614.12 Hz와 일치했습니다. 다만 CTC 설정은 한 카운트가 어긋나 있어서, 슬라이드의 코드대로라면 주기가 1.014초라는 점도 함께 적었습니다.

키패드 버그는 네 번의 세미나에 걸쳐 다뤘습니다. 구동 레벨과 키 인덱스를 바로잡았고, 누르고 있는 키가 반복 입력되는 문제는 처음엔 0.25초 지연으로, 다음 주에는 엣지 검출로 해결했습니다. 제 이름은 5×8 글리프 6개(48바이트)로 직접 그려 LCD에 띄웠습니다. 지난 발표에서 받은 질문에는 FEEDBACK 슬라이드 37장으로 답했고, 교재의 RS-232 그림 오류도 바로잡았습니다. 학기 말에는 다이나믹셀 로봇팔을 겨울방학 프로젝트로 정했습니다.
